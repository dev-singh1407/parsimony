# Parsimony — Roadmap and Milestones

**Today:** Wed 5 Aug 2026 · **Review 1:** mid-August (~10 days) · **Runway:** ~12 weeks to late October.

---

## 1. Why the report's timeline has to be replaced

The report schedules 16 weeks and places the baseline harness at weeks 1–2, the compressor at weeks 3–4, and
the cache at weeks 5–6. Following it literally means arriving at the mid-August review with an **unoptimised
baseline and zero working modules** — technically on schedule, and a bad review.

The available runway is also ~12 weeks, not 16. Two structural changes fix both problems.

**Change 1 — build the harness and the first two module tiers concurrently, not sequentially.** The report
treats weeks 1–2 as buying "no optimisation at all". That is correct as a scientific principle (every claim
is a difference against the baseline) but wrong as a delivery plan. M1 tier 1 (lossless normalisation) and
M2 tier 0 (exact-hash cache) are each ~150 lines, carry no research risk, and produce a *visible* token
reduction. Landing them alongside the harness costs about two days and completely changes what the review
looks like.

**Change 2 — vertical slices, not horizontal layers.** Build a thin end-to-end path first (ingest → one
module → mock provider → ledger → CLI trace), then thicken it. The alternative — finish all of L1, then all
of L2 — means nothing runs until week 6. A walking skeleton that runs on day 4 is worth more than a perfect
infrastructure layer that runs on day 40, because it surfaces integration errors while they are still cheap.

**What is deliberately not compressed:** the corpus freeze, the gold answers, and the ledger schema. Those
are the things that cannot be fixed later (ADR-014, ADR-015).

### Review 1 — ~Sat 15 Aug

**Demo script (12 minutes).**

1. **The gap, in one figure** — Figure 2 from the report (18/82 prefill/decode split). One sentence: the
   literature optimises the 18 %.
2. **Live**: `parsimony chat "What is 847 * 23?" --trace` → deterministic tier, **0 model tokens**, exact
   answer. Contrast with the same query at baseline.
3. **Live**: a multi-sentence prompt → trace table showing tier 1 and tier 2 token deltas, then the *same*
   prompt with a number in it where a tier-3-style edit is **reverted by the fidelity gate**. Showing the
   safety mechanism firing is more persuasive than showing a large reduction.
4. **Live**: repeat a paraphrased query → cache hit, zero model tokens.
5. **The 4-cell ablation table**, with the honest note that the sum of the parts already exceeds the measured
   stack — which is Contribution 1 in miniature, appearing on day 10.
6. **Architecture in one slide**: the layering diagram + "stage order is configuration, which is what makes
   Gap 3 answerable".
7. **State plainly**: latency numbers are from a mock provider and are pipeline-correctness evidence, not
   performance evidence. Ollama lands in Sprint 2. Saying this before being asked is worth more than the
   numbers would be.

**What makes this a strong review.** Not the size of the token reduction — it will be modest. It is that the
*measurement instrument* exists, the ablation harness runs, the safety gate visibly fires, and the schedule
from here is concrete. Reviewers of final-year projects are calibrated on whether the foundation is real.

## 4. Definition of done, per module

A module is done when all seven hold:

1. Implements `Stage`; declares `reads`/`writes` accurately.
2. Unit tests with no mocks (modules are pure functions of `(ctx, cfg)`).
3. Contract test passes against the shared suite for its protocol.
4. Emits the correct `TransformKind` — verified by a behaviour probe, not just by inspection.
5. Adds its ledger fields; schema bumped additively (ADR-014).
6. Every threshold lives in `ParsimonyConfig` — zero float literals in the module.
7. One line in `docs/02-module-specs.md` reconciled against what was actually built.
